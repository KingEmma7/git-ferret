# AGENTS.md

Instructions for AI agents working in this repository. Read this before changing code.
`CONTRIBUTING.md` is the human-facing source for the same rules; if the two disagree, follow
`CONTRIBUTING.md` and fix this file.

## What this project is

git-ferret is a read-only reporting tool for auditing many local git repositories at once. It finds
branches that are merged, unpushed, diverged, or safe to delete, and it never deletes anything
itself. The only write path is an explicit `local --update`, which fast-forwards clean worktrees.

Stack: Python 3.14, typer and rich for the CLI, pytest for tests, ruff for formatting and linting,
pyright in strict mode for types, and uv for the locked environment. There is no Node.js toolchain
and there must not be one.

## Commands

Run these from the repository root. When `.venv` exists but is not active, plain `make` uses the
system interpreter and will not find ruff or pyright; run `uv run --no-sync make <target>` or pass
`PYTHON=.venv/bin/python`.

| Command | What it does |
|---|---|
| `uv sync --all-extras --locked` | Install the project and every dev extra from `uv.lock` |
| `make install` | The pip equivalent, installing all extras |
| `make sync` | `uv sync --all-extras --locked` |
| `make hooks` | Set this repository's `core.hooksPath` to `.githooks` |
| `make format` / `make format-check` | Format, or check formatting, with ruff |
| `make lint` / `make lint-fix` | Lint, or lint and apply safe fixes |
| `make check-spdx` | Check the SPDX header on every Python source file |
| `make typecheck` | Run pyright in strict mode |
| `make test` | Run the pytest suite |
| `make coverage` | Run the suite with terminal, XML, and HTML coverage reports |
| `make build` | Build the sdist and wheel, then run `twine check` |
| `make audit` | Scan dependencies with `pip-audit` |
| `make check` | format-check, lint, check-spdx, typecheck, and test |
| `make ci` | Everything CI runs, including coverage, build, and audit |
| `make help` | List the targets |

`make check` is the fast gate and is what a pull request must pass; `make ci` is the full gate and
adds coverage, build, and audit. Run `make check` before claiming a change is complete, and
`make ci` when you touched dependencies, packaging, or code whose coverage matters. The pre-push
hook runs `make typecheck test`, and the pre-commit hook formats and lints staged Python files.

## Hard constraints

- Read-only by default. `local --update` is the only write path, and only for a clean worktree
  behind its upstream. Do not add another write.
- Tests use real git repositories, never a mocked git. Fixtures are built with `tests.helpers`.
- The report is markdown with no ANSI escapes and no tables in the file. Terminal styling happens
  only in `report.emit` when stdout is a TTY.
- Emoji are decorative. The bracketed marker (`[NOT PUSHED]`, `[SAFE TO DELETE]`) carries the
  meaning on its own. Never move information into the emoji.
- Findings never change the exit code. `0` means the run completed; `1` is a usage error; `2` is
  reserved. Do not turn a finding into a failing exit code.
- Python 3.14 or newer, and git 2.38 or newer because the merge test uses
  `merge-tree --write-tree`.
- Existing README promises must keep holding: read-only behaviour, exit codes, and markdown output.
- No product feature should arrive without tests. No new dependency without a reason.

## Conventions

- Every file under `git_ferret/`, `tests/`, and `scripts/` starts with:
  ```python
  # SPDX-FileCopyrightText: 2026 Fran
  # SPDX-License-Identifier: GPL-3.0-only
  ```
- Write a module docstring and docstrings at public-function boundaries. Explain why a rule exists,
  not what the next line does.
- Keep pyright strict clean. Add explicit types at boundaries and avoid `Any` unless it is genuinely
  the type.
- Imports are sorted by ruff: standard library, third-party, then local. Use `from __future__ import
  annotations` in modules that benefit from it.
- Prose is ASCII and avoids em-dashes. Use a hyphen or a comma.
- Commits use Conventional Commits: `type(scope)?: description`, lowercase imperative description,
  no trailing period. Allowed types: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`,
  `refactor`, `revert`, `style`, `test`. Merge, revert, fixup, and squash commits pass through.
- Branch names are `type/kebab-case-slug`, with the same type as the PR title.
- Do not add `Generated by` or `Co-Authored-By` footers to commits.
- Update `README.md` when behaviour is user-facing. Do not restate the Makefile targets or
  `pyproject.toml` configuration in the README's prose; point at them. The command table above is
  orientation, and the `Makefile` stays authoritative.

## Testing

- Tests live in `tests/test_<module>.py`, named for the module or behaviour they cover. Shared
  fixture builders live in `tests/helpers.py`; there is deliberately no `conftest.py`.
- Build real repositories with `make_repo`, `commit`, `clone_local`, and `run` from
  `tests.helpers`. The behaviour worth protecting is git's own, so mocking git tests nothing useful.
- Coverage is measured over `git_ferret/` with a floor of 95 in `pyproject.toml`. Do not duplicate
  an existing test just to move the number; cover a distinct path or a distinct failure mode.
- The suite runs on Linux, macOS, and Windows. Keep subprocess decoding on UTF-8, build paths with
  `pathlib` rather than joining strings with `/`, and remember that a console may not render emoji.
- New scripts under `scripts/` need unit tests too. `scripts/check_commit_msg.py` runs on every
  commit, so its edge cases matter.

## GitHub

- Issue and pull request body shape comes from `.github/ISSUE_TEMPLATE/` and
  `.github/PULL_REQUEST_TEMPLATE.md`. Do not invent a second format here.
- `gh pr create` does not apply the pull request template. Pass a filled copy with `--body-file`.
- The merge gate in `.github/workflows/ci.yml` requires lint, type-check, the cross-platform test
  job, coverage, build, and audit.
- release-please is the only release path. Do not hand-edit versions, tags, or the release manifest;
  it opens the release pull request and the release workflow publishes the draft.
- Do not hand-apply Dependabot's automation labels. Dependabot uses the `uv` ecosystem so its pull
  requests update `uv.lock` as well as `pyproject.toml`.

## Where to look

- `Makefile`: every local command and what `make check` includes.
- `pyproject.toml`: dependencies, extras, ruff, pyright, pytest, and the coverage floor.
- `git_ferret/`: the package. `cli.py` is the entry point, `gitcmd.py` is the only module that
  shells out to git, `report.py` renders the markdown, and `analysis/` holds the verdicts.
- `tests/`: the suite plus `tests/helpers.py`, the real-repository fixture builders.
- `scripts/`: `coverage_summary.py`, `check_commit_msg.py`, and `check_spdx.py`.
- `.githooks/`: `commit-msg`, `pre-commit`, and `pre-push`, which chain to any global hooks.
- `.github/`: workflows, the composite setup action, issue and pull request templates, and
  Dependabot configuration.
- `docs/superpowers/specs/`: design notes. They record decisions at the time; do not rewrite them
  to match later code.

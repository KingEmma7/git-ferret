# Contributing to git-ferret

Thanks for taking the time to improve the tool. This guide covers the local workflow, the checks,
and what a pull request needs. If you are an AI agent, read [`AGENTS.md`](AGENTS.md) first: it is the
agent-facing counterpart to this guide, and this file is authoritative if the two disagree.

## Development setup

You need Python 3.14 or newer, git 2.38 or newer, GNU make, and
[uv](https://docs.astral.sh/uv/) (recommended) or pip. On Windows, `make` is not installed by
default; install it, or run the underlying `python -m ...` commands directly.

```console
$ git clone https://github.com/fran2889/git-ferret
$ cd git-ferret
$ uv sync --all-extras --locked
$ make hooks
$ uv run --no-sync make check
```

`make install` is the pip route: it installs every optional-dependency group at once. `make sync`
is the uv route. The lockfile is committed, and CI installs with `uv sync --locked`, so a dependency
change has to update `uv.lock` in the same pull request. Dependabot uses the `uv` ecosystem for that
reason.

`make hooks` points this repository's `core.hooksPath` at the checked-in `.githooks/` directory,
and the hooks chain to any global hooks you already have, so nothing is hidden. `make check` must
pass before you open a pull request.

The `uv run --no-sync` prefix uses the environment that `uv sync` just built, without resolving it
again or requiring activation. If you would rather activate it, `source .venv/bin/activate`
(`.venv\Scripts\activate` on Windows) and then plain `make check` works.

If the environment breaks, rebuild it. Every script in `.venv/bin` records the absolute path of the
interpreter that created it, so uninstalling or upgrading that Python makes all of them fail:

```console
$ rm -rf .venv
$ uv sync --all-extras --locked
```

## Make targets

`make help` lists every target, and the `Makefile` is authoritative. The ones you will use most:

| Target | What it does |
|---|---|
| `make check` | The fast local gate: format check, lint, SPDX headers, types, tests |
| `make test` | The pytest suite |
| `make typecheck` | pyright in strict mode over the package, tests, and scripts |
| `make coverage` | The suite plus terminal, XML, and HTML coverage reports |
| `make build` | Build the sdist and wheel, then run `twine check` |
| `make audit` | Scan dependencies with `pip-audit` |
| `make ci` | The full local gate: format check, lint, SPDX, types, coverage, build, and audit |
| `make hooks` | Point this repository at `.githooks` |
| `make clean` | Remove build artifacts and caches |

Every Python target runs `python -m ...`, so `PYTHON` selects the interpreter. When the environment
is not active:

```console
$ make check PYTHON=.venv/bin/python
```

`uv run --no-sync make check` does the same thing from the locked environment without activating it.

## Git hooks

`make hooks` sets `core.hooksPath` to `.githooks` for this repository only. It does not change your
global git configuration, and it does not install anything outside the checkout.

- `pre-commit` runs `ruff format` and `ruff check --fix` on staged Python files, then re-stages
  them. Only the staged files are touched.
- `pre-push` runs `make typecheck test`, so the two slower gates fail before CI sees them.
- `commit-msg` runs `scripts/check_commit_msg.py`, which enforces the Conventional Commits shape
  and rejects a description that is uppercase, non-imperative, or ends with a period.

The hooks call a configured global `core.hooksPath` first, because setting a local path otherwise
hides the hooks a person already had. The global hook must succeed before the local work runs.

The commit-message checker has unit tests in `tests/test_check_commit_msg.py`. It is code that runs
on every commit, so its edge cases are worth covering.

## Branches, commits, and pull requests

- Branch names are `type/kebab-case-slug`, where `type` is the Conventional Commits type used in
  the pull request title, for example `fix/shallow-clone-warning` or `docs/releasing-runbook`.
- Commit subjects use Conventional Commits: `type(scope)?: description`. The allowed types are
  `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, and `test`.
  The description starts lowercase, is imperative, and has no trailing period. Merge, revert,
  fixup, and squash commits pass through unchanged.
- Do not add `Generated by` or `Co-Authored-By` footers to commit messages.
- A pull request title is squash-merged and parsed by release-please, so it must also be a
  Conventional Commit.
- Run `make check` before pushing. `make ci` adds coverage, the build, and the dependency audit, but
  reaches the network and is slower.
- Fill in `.github/PULL_REQUEST_TEMPLATE.md`. `gh pr create` does not apply the template
  automatically; pass a filled copy with `--body-file`. Keep the Summary to one to three bullets,
  one behaviour change each, and name the automated check plus any manual command in the Test Plan.
- The templates in `.github/ISSUE_TEMPLATE/` apply the `bug` and `enhancement` labels. Add any other
  label deliberately. Do not hand-apply Dependabot's automation labels.

## Tests

- The suite builds real git repositories and runs real git commands. Mocking git would test the
  mock, and the behaviour worth protecting here is git's own.
- Fixture builders live in `tests/helpers.py`: `make_repo`, `commit`, `clone_local`, and `run`.
  There is no `conftest.py`; a test calls the builder at the exact path it wants.
- Tests are named for the module or behaviour they cover, for example `tests/test_report.py` or
  `tests/test_end_to_end.py`.
- Add tests for behaviour changes. A bug fix needs a test that failed before the fix; a feature
  needs tests for the new path.
- Coverage is measured over `git_ferret/` with a floor of 95 in `pyproject.toml`. Cover a distinct
  path or failure mode rather than duplicating an existing test to move the number.
- The suite runs on Linux, macOS, and Windows. Subprocess output is decoded as UTF-8, paths are
  built with `pathlib`, and the report survives a console that cannot render emoji.
- New scripts under `scripts/` need unit tests. `scripts/check_spdx.py` and
  `scripts/check_commit_msg.py` are both covered.

## Layout

- `git_ferret/cli.py`: typer commands, usage errors, and the run loop.
- `git_ferret/gitcmd.py`: the only module that calls `subprocess`; every git invocation goes here.
- `git_ferret/discovery.py`: finding repositories and worktrees without descending into them.
- `git_ferret/gitops.py`: fetch, base refs, branch state, and the merge test.
- `git_ferret/analysis/`: the verdicts for `local`, `remote`, and `merged`.
- `git_ferret/report.py`: markdown rendering and the TTY-only rich path.
- `tests/`: the suite and its fixture builders.
- `scripts/`: coverage summary, commit-message checker, and SPDX checker.
- `.github/`: CI, release automation, and the issue and pull request templates.

## Documentation

Update `README.md` when user-facing behaviour changes. The README is the user manual. Do not
restate the `Makefile` targets or the `pyproject.toml` configuration in prose; point at them
instead.

## CI

The merge gate in `.github/workflows/ci.yml` requires lint, type-check, the cross-platform test
job, coverage, build, and audit. Dependency review is a separate check; its `dependency-review`
context must also be required in the `Protect main` ruleset. release-please is the only release
path; do not hand-edit versions or tags.
